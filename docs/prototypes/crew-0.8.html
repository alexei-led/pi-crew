Tool-first

The lead gets the same status via list

  • Pending delivery: stored by the bridge, not yet accepted into a lead turn. Include oldest age and last known failure class.
  • Waiting on lead: an open worker question. It may already have reached the lead.
  • Needs you: an explicit request for operator input, not an inferred worker state. If the host can’t provide a reliable signal, omit this count.

Browsing doesn’t send, reply, or acknowledge. Native Claude agents continue to use their own tools and delivery path.

Read the sequence
  1. Report stored. The bridge stores api’s question before it sends a transport receipt.
  2. Submission deferred. The host drops this submission while the lead is busy. Keep the report in the inbox and schedule a retry without sleeping inside the dispatcher.
  3. Bridge restarts. It replays api’s pending question and receives docs’ DONE. Replay of a pending ID updates the existing queue item; it doesn’t enqueue another turn.
  4. Another run makes progress. The lead is now available. api is still in retry backoff, so docs’ DONE can submit once its git checks finish. The bridge removes it after ack.
  5. Question accepted. api’s retry becomes due and the host is ready again. The host accepts the lead turn and the bridge clears pending delivery. The question is still open until the lead replies.

Ownership and contracts

Keep delivery separate from display

  • Bridge: Own durable inbox and replay. Key reports by message ID and group them by worker identity and run ID. DONE checks must not hold unrelated runs behind a global FIFO.
  • Mod: Own scheduling and host prompt submission. Take one eligible run head at a time in arrival order across eligible runs. A dropped or failed submission defers that head, not the dispatcher. Wake on new work or when a retry is due, without relying on an unverified host readiness hook.
  • Progress: Bundle preceding progress with that run’s next important report or offer it on the next user prompt. Bound each digest and show how many updates were omitted. Only acknowledge the included or explicitly counted IDs once the host accepts it. Full text stays subject to normal history retention.
  • Tools and UI: Read queue/health snapshots and distinguish unknown state during disconnect from an empty queue. Browsing cannot change delivery state.

Failure boundary and acceptance

Make recovery testable

  • Not exactly-once: Record accepted IDs before acknowledging so ordinary replay can retry ack without another turn. Without host idempotency, a crash between prompt acceptance and recording that acceptance can still duplicate a turn.
  • Not durable until receipt: A broker restart can lose reports that haven’t reached the bridge. Don’t treat a queued send as proof of storage.
  • Release gate: Exercise a busy lead, a bridge restart, a thrown submission, and a failed ack. Verify per-run order, progress overflow counts, and recovery without /crew or plugin reload. Opening the pane must not alter delivery.
